# Review and status, 27 October 2026

Scope: everything built from 24 to 27 October (64 commits before this review): the base stack (MVP 1-9), professionalisation
(backups off-site, CI, new-PC rehearsal), long-term memory, the requirements-checker pilot, the Topic Desk,
Mission Control (missions, events, deep research, wikis, chat, Stack page), subscription-only, and the builder.

## Verdict

The stack works end to end and is unusually well secured and recoverable for a home setup: per-agent keys and tool
grants, isolated web reading, sandboxed coding, encrypted backups with a weekly restore drill, a rehearsed new-PC
path, $0 running cost. It is **not yet production grade as a codebase**: it grew fast, feature by feature, with
almost no automated tests, a few large files that grew by patching, documentation that only now exists, and several
features that were built to "works once" but not to "runs unattended for months". The biggest operational risk is
not software at all: **the PC has 16 GB RAM and runs at its limit** (WSL VM hard-stopped once on 27 Oct).

## Half-built or not thought to the end

1. **Builder never deployed for real.** Build #1 is parked until the ChatGPT reset; `ops/deploy.py` has not run on a
   real change, `ops/windows/*` changes cannot be deployed (WSL cannot write Windows paths), and there are no
   Forgejo pull requests (no write token: the review lives only in Mission Control).
2. **Chat token use.** Every turn re-sends the last 16 messages, including extracted documents (up to 120 k chars
   each). Hermes has server-side sessions (`X-Hermes-Session-Id`, Responses API) that would avoid this. Together
   with the builder this is what exhausted the ChatGPT Plus 5-hour window on 27 Oct.
3. **Usage limits are handled, not managed.** Missions and builds wait and resume; chat just errors. There is no
   budgeting of the subscription's 5-hour window across chat, missions, builder and memory, and no warning before
   the limit.
4. **Event triggers lightly tested.** Only one replayed SEC filing went through the full path; price and news
   triggers were checked against live data but have not fired for real; GDELT is always rate-limited (dead code).
5. **Mission wikis are append-only.** Pages are rewritten per result without dedup across pages, contradiction
   handling or a lint/curation pass (the main vault wiki has the curator; mission wikis do not).
6. **Phase 3 (resource limits) not built.** Limits are shown, not editable; the WSL total needs a Windows-side step.
7. **Telegram buttons are links only.** Real in-chat actions (approve, run) would need callback handling inside
   Hermes' bot loop; `/memory approve` in Telegram still does not work (the app does).
8. **New-PC path does not know the newest parts.** Not covered: `tailscale serve` :8448, the Windows host-probe task,
   the builder image's build argument (works by default), first-time setup of the `mission` and `builder`
   Hermes profiles, and the dashboard's own API key in Hermes' `.env` (now synced by `configure.sh`).
9. **`versions.lock` is stale** (24 Oct): it misses Hindsight, pgvector, the builder, Mission Control and others.
10. **The Hermes image warns "install out of sync (uv.lock)"** on every command: the image was extended with pip
    installs on top of a uv-managed venv. Harmless today, a trap at the next upgrade.
11. **Growing files nobody prunes**: `events.jsonl`, run logs, build logs and diffs, chat files and uploads,
    `seen_events`, `/srv/ai/missions/app/uploads`. Small now, unbounded over months.
12. **Requirements checker and MVP 3 import** stopped at pilot / waiting for input.

## Technical debt

- **No unit tests** for the runner (`missions.py` 1 034 lines, `mission_extras.py`, `builds.py`), the app server
  (917 lines) or the front end (1 193 lines JS). CI cannot catch logic errors; two bugs today were found only by
  manual drills (`mission_context` deleted, rollback merge of a local branch).
- **Monolithic runner.** One process schedules missions, watches events, runs builds, measures resources and writes
  state every 4 s (with `docker exec psql` each time). A crash stops all of it (systemd restarts it).
- **Front end grown by patches**: CSS in v1/v2/v3 layers, one global script, re-render logic with special cases.
  Works, but every change is risky without tests.
- **State through files** (inbox, results, state.json) instead of a small API between runner and app: simple and
  robust, but polling-based and racy at the edges.
- **Duplicate surfaces**: Open WebUI (500 MB RAM) is now largely redundant with Mission Control chat; Ollama exists
  only for the smoke test.
- **Workarounds worth replacing**: Git Bash path mangling (`MSYS_NO_PATHCONV`), the builder's world-writable
  workbench, the `docker run` per event check (container start every 10 min).

## Missed opportunities

- **A local $0 fallback model.** Subscription-only means everything stops when ChatGPT pauses. A small local model
  (Ollama is already running) could answer simple chat turns and memory extraction during pauses: free, private,
  slower. Needs RAM, see below.
- **Hermes sessions and runs API** for chat (history server-side, real stop, tool events) instead of re-sending.
- **Codex as the builder's engine.** Hermes has a Codex runtime; OpenAI's coding agent on the same subscription
  may be stronger and more token-efficient for code than generic tool use.
- **Hermes kanban** for multi-step work was evaluated but not used; the builder and deep research reimplement parts.
- **A Forgejo write token** (one manual step) would give real pull requests, review comments and history in Forgejo.
- **Per-mission model and effort** (briefings on the fast model, deep research on the strong one) to stretch the
  subscription window.
- **Notification preferences** (quiet hours, per-event channels) before the alert volume grows.

## What should have been done differently

- **Tests before features.** A minimal test harness for the runner and app (pytest with a fake Docker/LiteLLM)
  early on would have caught today's regressions and made the builder's checks meaningful.
- **Docs as part of each feature**, not at the end.
- **Measure the subscription budget before adding token-hungry features** (deep research, builder, document chat).
- **Hardware first**: 16 GB RAM was already tight at MVP 7; everything since added memory pressure.

## Recommended next steps (in order)

1. **Hardware**: 32 GB RAM (about €70; the board takes 64 GB). Removes the main stability risk and makes a local
   fallback model possible.
2. **Finish and prove the builder**: review and deploy Build #1 by tap; add a Forgejo write token for real PRs.
3. **Chat on Hermes sessions** (stop re-sending history) + per-mission model choice: halves token use.
4. **Test harness**: pytest for `missions.py`, `builds.py`, `server.py` with fakes; run it in CI; ask the builder to
   extend it with every assignment.
5. **Retention**: prune events, logs, chats, uploads (keep 90 days) in a nightly job; refresh `versions.lock`.
6. **New-PC path**: add the new services, ports and Windows task to `new-machine.sh` / `host-setup.ps1` and the
   rehearsal.
7. **Mission wiki curation**: weekly pass that merges duplicates and flags contradictions, like the vault curator.
8. **Phase 3**: editable resource limits.
