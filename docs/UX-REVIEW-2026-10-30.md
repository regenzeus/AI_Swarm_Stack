# UX review of Mission Control, 2026-10-30

Requested in chat on 2026-10-30 after the owner found Start mission broken (FND-52): *how many issues of this kind are
there, and how do we find them without the owner using every feature?* The requirements are APP-24 (find them) and APP-25
(what the review fixed). The findings are FND-53 to FND-61 in `requirements/findings.yaml`.

## How the review was done

| Pass | What it covered | What it found |
|---|---|---|
| Static lint (`ops/app_lint.py`) | The four app scripts joined in load order, checked by ESLint for undefined names, redeclarations and unreachable code | Clean now. On the code before the fix it reports `app.js:1499: no-undef: 'watch'`, which is the Start mission bug. Nothing else of that kind. |
| Click-through (`ops/ui_crawl.js`) | 70 screens reached from Home and 279 taps (every button, chip, fold and switch on each kind of screen) at phone width, forms filled in, every write recorded instead of sent | One failure: the chat's copy buttons (FND-58). No screen failed to load and no tap threw. |
| Kept errors | The app's own error reports | None to read. They lived only in the container's log, which a deploy wipes (FND-53). |
| Visual pass | Home, Agents, a mission, New mission, Stack, the Wiki map and the Swarm maps at 375 px | FND-55 to FND-57 and FND-59 to FND-61, and the proposals below |

So the answer to *how many of this type* is one more, a small one. The Start mission bug was the only error in the code
that breaks a tap. The other problems were design problems: things that work but bury what the owner wants to see.

## How this stays in order without the owner testing it

1. **Every landing lints the scripts.** `ops/check.sh` runs `ops/app_lint.py` in the builder's image, and `ops/land.sh`
   refuses a change that fails it. The Start mission bug would have been stopped on 28 October. ESLint comes with the
   builder and CI images, which the deploy of this review rebuilds. Where ESLint is missing (a plain `make check` on the
   host), the step is skipped and the output says so.
2. **Every error the owner hits becomes an alert.** The server keeps the newest 500 and the health board raises
   *Mission Control (the app)* while any came in the last 24 hours. The alert names the most frequent error and the
   screen it happened on, so the health doctor sees it before the owner has to mention it.
3. **Forms are tested by running them.** `tests/test_app_forms.py` and `tests/test_ux_review.py` run the real handlers
   in node, not just search their text.
4. **The click-through can be repeated.** `ops/ui_crawl.js` runs in any browser on the app. It records writes instead of
   sending them, so it creates, approves and deletes nothing. Proposal 3 makes it a weekly job.
