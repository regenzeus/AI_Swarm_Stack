## Answers to the owner's questions

### Do we use the RAG? Two knowledge systems?

There are three memory layers, and they are not rivals:

| Layer | What it holds | Who writes | Who reads |
|---|---|---|---|
| **The wikis** (LLM wiki) | curated pages per mission/topic and the vault wiki | the curator, each mission's wiki step, the Librarian | everyone, through search |
| **qmd** (the RAG) | the search index over the wikis, your notes (raw), journals, specs, code summaries | qmd itself, from the vault | your assistant, every mission run at its start, agents with vault search |
| **Hindsight** | facts from your conversations (222 now) | Hindsight, after chats | your assistant, missions (memory_recall) |

So the wiki is *what* the stack knows and qmd is *how agents find it*. Measured over the last five days (runtime
record): 111 qmd searches and reads (your assistant 50, missions 61), 44 wiki lookups at the start of runs (they go
through qmd), 37 Hindsight recalls. It is used, every day, more each day (11 → 62 a day).

**Where it is not used and should be:** the web researcher (scout) ran 1,566 web searches and never once checked the
vault. It cannot, by design (it reads the untrusted web and must hold nothing private), so the agent that calls it
must look first: missions searched the vault 29 times against 228 research calls. Recommendation: a research memo in
the vault for every research answer, and the mission's first call a vault search for the same question (a prompt
change with its replay). Two collections are still empty: `bulk-mail` and `bulk-chats` wait for your exports
(MVP 3's import). The index has 244 orphaned chunks (18 %); the Librarian cleans them weekly (Wednesday).

### mqtt-trace: requirements traced in an open-source broker (mochi-mqtt)

One run (02:16, task 110, 10 minutes, about 3.0 M tokens). The job: for each of the MQTT 5 requirements, the file and
line that fulfils it, and every requirement the code does not meet. The key took every requirement ID out of the
code, and nine deviations were planted beforehand.

| Area | Result |
|---|---|
| Requirements placed in the right function | 94 of 117 (80 %; the pilot by hand: see spec/README.md) |
| Planted deviations found | **9 of 9** |
| Real defects of the broker the key knows | **4 of 4** |
| Every requirement answered | yes (133 of 133) |
| False alarms (gaps the key reviewed and rejected) | 1 (MQTT-3.1.2-1: the code there is only a MAY) |
| Gaps beyond the key, for your review | 21 |

The tracer reported 25 gaps that the key did not know, and the key, as written, counted every one as a false alarm
(104 of 152). I read four of them in the code. Three are real defects of mochi-mqtt itself:
- inline subscribers on `x/#` are gathered from the wrong node (`topics.go` line 615);
- a user name is never checked as UTF-8 (`packets.go` line 427);
- an expired message is clamped to one second and sent anyway (`clients.go` line 537).

The fourth is only a MAY. The key now holds those three as real defects, and the scorer lists any gap it doesn't
know for review instead of counting it wrong (TRL-13). Scored again on the same delivered trace: **108 of 132
(82 %)**. The 21 gaps for review are in the run's report under Trials. Each one is either a real defect the key
doesn't know yet or a false alarm, and only a reading of the code can tell which. The stack-trace trial (tonight,
01:00, our own code against our own requirements) uses the same rule: a gap on a requirement the register calls met
is a possible finding, not a mistake.
